# NotEditor 리브랜딩과 데스크톱·웹 배포

**날짜:** 2026-08-26
**상태:** 구현 완료 — 배포 경로 두 개(Docker 실행, 설치 파일 빌드)만 기기 미검증

## 왜 하는가
현재 제품명과 저장소·Python 패키지 이름이 PDF 문서 합치기 한 기능만 표현하고, 문서 합치기와
Samsung Notes 필기 이전의 UI 위계도 서로 다르다. Windows 전용 네이티브 파일 대화상자에
의존해 다른 사람이 설치하거나 웹에서 사용하기 어렵고, 설치 과정도 두 스크립트로 나뉘어 있다.

## 목표
제품 전체를 `NotEditor`로 리브랜딩하고, 문서 합치기와 필기 옮기기를 동급 탭으로 제공한다.
같은 핵심 처리 코드를 Windows 데스크톱 앱과 Docker 기반 웹앱에서 사용하며, GitHub Releases의
Windows 설치 파일과 PowerShell 원터치 설치를 모두 제공할 수 있는 배포 구조를 만든다.

## 성공 기준
- [x] 저장소 폴더가 `C:\dev\NotEditor`, Python 패키지가 `noteditor`가 된다.
- [x] 앱 제목·로그 경로·바로가기·문서·설치 산출물에서 제품명이 `NotEditor`로 통일된다.
  내부 식별자 `PdfComposerError`·`ComposerSession`은 옛 이름이 남아 있으나 사용자에게 보이지 않는다.
- [x] 문서 합치기와 필기 옮기기가 같은 위계의 탭으로 전환된다.
- [x] 문서 합치기의 세 패널 제목부/내용부 경계 높이가 일치한다(`.panel-header` 73px).
- [x] 데스크톱과 웹에서 PDF/SDOCX 업로드 및 처리 중 로딩 표시가 보인다.
- [x] 웹에서 업로드, 미리보기, 문서 합치기 저장, 필기 이전 저장을 실제로 수행할 수 있다.
  실제 uvicorn 서버에 HTTP로 붙어 업로드 → 쪽 미리보기 → 범위 파싱 → 합치기 내려받기까지
  확인했고, 결과 PDF의 쪽 순서·내용이 지정한 순서와 일치했다. 필기 이전 저장은 인프로세스
  테스트(`tests/test_web.py`)까지 검증했다.
- [ ] Docker 이미지로 웹앱을 실행할 수 있고 임시 업로드는 세션별로 격리·정리된다.
  세션 격리·정리는 검증했다. **이미지 빌드·실행은 미검증** — 개발 기기에 Docker가 없다.
  대신 `test` 워크플로에 `docker build` 잡을 추가해 CI에서 확인하도록 했다.
- [x] PowerShell 한 번 실행 설치와 GitHub Releases용 Windows 설치 파일 빌드가 모두 마련된다.
  `install.ps1`은 Windows PowerShell 5.1에서 실제로 끝까지 성공한다(BOM 수정 후). 설치 파일
  빌드는 `windows-release` 워크플로에 있으나 **태그 릴리스를 한 번도 실행하지 않았다.**
- [x] README에 구조, 설치, 웹 실행, 배포, 테스트 방법이 최신 상태로 기록된다.
- [x] 전체 자동 테스트가 통과한다(89개, Python 3.14.7 / Windows 11).
- [x] 비공개 `kynbeen/NotEditor` GitHub 저장소에 코드와 핸드오프가 푸시된다.

## 범위 밖
- 특정 클라우드 서비스의 계정 생성, 결제 수단 연결, 운영 도메인·TLS 설정.
- Samsung Notes 자체를 웹에서 실행하거나 SDOCX 형식 전체를 편집하는 기능.
- Windows 이외 운영체제용 네이티브 설치 패키지.

## 제약
- PDF 최종 출력은 기존처럼 원본 PDF 객체를 복사해 품질 손실을 피한다.
- 필기 이전은 원본 SDOCX 획 데이터를 재직렬화하지 않고 보존한다. 미리보기 디코딩은 읽기 전용이다.
- 웹 업로드는 사용자 세션별 임시 디렉터리에 두고, 만료 또는 명시적 초기화 시 삭제한다.
- 데스크톱 앱 기능을 제거하지 않는다. 사용자가 데스크톱과 웹 동시 지원을 선택했다.
- Python 소스는 루트에 평탄화하지 않고 `noteditor` 패키지 아래 둔다. import 경계와 정적 자원
  패키징을 명확히 유지하기 위해서다.

## 고려했다가 안 한 것
| 대안 | 왜 안 했나 |
|---|---|
| Python 파일을 저장소 루트에 모두 평탄화 | 테스트·문서·배포 파일과 런타임 코드가 섞이고 패키지 자원 경계가 사라진다. |
| 웹앱만 남기고 데스크톱 앱 제거 | 사용자가 두 실행 형태를 모두 유지하기로 선택했다. |
| GitHub Pages에 처리 앱 배포 | PyMuPDF와 SDOCX 처리는 Python 서버가 필요해 정적 호스팅만으로 동작하지 않는다. |
| 특정 클라우드에 즉시 배포 | 사용자가 업체 중립적인 Docker 배포 준비를 선택했다. |
| 내부 식별자(`PdfComposerError`, `ComposerSession`)까지 개명 | 사용자에게 보이지 않는 이름이다. 전 파일을 건드리는 변경 대비 얻는 것이 없다. 리브랜딩의 성공 기준은 사용자 노출 문자열이다. |
| 개발 기기에 Docker Desktop을 설치해 검증 | 검증 하나를 위해 큰 도구를 상시 설치하는 것은 과하다. `test` 워크플로의 `docker build` 잡이 모든 푸시에서 대신 확인한다. |
| GitHub Actions 정기 실행(cron)으로 무료 등급 서버 깨우기 | 사용자가 UptimeRobot을 선택해 등록을 마쳤다. 다만 무료 인스턴스 시간이 빠듯해져 "낮 시간대만 깨우기"가 필요해지면 이 경로가 다시 후보가 된다 — UptimeRobot 무료 등급에는 시간대 지정이 없다. |
| Render 워크스페이스를 여러 개 만들어 무료 시간 늘리기 | 문서에 근거가 없고 사실상 할당량 우회다. 운영을 기댈 근거가 못 된다. |
| 매니페스트로 PWA 창을 최대화 상태로 열기 | 웹 앱 매니페스트에는 창 크기·창 상태를 지정하는 항목이 아예 없다(MDN 멤버 목록 확인). `"display": "fullscreen"`은 데스크톱에서 대체로 `standalone`으로 되돌아가고, 동작해도 최대화가 아니라 전체화면이다. 유일하게 검증된 방법은 바로가기에 `--start-maximized` 플래그를 붙이는 것이며 이는 앱이 아니라 기기별 설정이다. |

## 열린 질문
- Docker 이미지를 실제로 실행해 본 적이 없다. 개발 기기에 Docker가 없다.
- 태그를 붙여 `windows-release`를 돌린 적이 없다. 설치 파일(`.exe`) 산출은 미검증이다.

## 변경 이력
- 2026-08-26: 사용자 선택 1A·2A·3B·4C에 따라 데스크톱+웹, Docker, 비공개 GitHub,
  두 가지 Windows 설치 방식을 확정했다.
- 2026-08-27: `LAPTOP`에서 새로 설치·실행·테스트·웹 종단 검증을 마치고 성공 기준을 실측으로
  채웠다. `install.ps1`이 Windows PowerShell 5.1에서 파싱 에러로 죽던 문제(UTF-8 BOM 없음)를
  고쳤다. 남은 미검증 항목 두 개(Docker 실행, 설치 파일 빌드)와 CI 미실행을 열린 질문으로 옮겼다.
- 2026-08-28: **CI 미실행 문제가 해소되어 열린 질문에서 뺐다.** 이날 푸시(`a2e07a4`)에서
  `test` 워크플로가 정상 실행돼 통과했고, `docker build` 잡도 함께 성공했다. 다만 이미지를
  **실행**해 본 적은 여전히 없어 해당 성공 기준은 미완으로 둔다. 무료 등급 상시 가동을
  UptimeRobot으로 처리하면서 접은 경로 세 개(Actions cron, 워크스페이스 분산, 매니페스트 기반
  PWA 최대화)를 추가했다. 세션 기록은
  `docs/handoffs/2026-08-28-01-웹-상시-가동과-헬스-핑-정리.md` 에 있다.
