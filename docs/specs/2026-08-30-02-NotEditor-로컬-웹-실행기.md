# NotEditor 로컬 웹 실행기

**날짜:** 2026-08-30
**상태:** 완료

## 왜 하는가

현재 설치된 로컬 PWA 바로가기는 이미 배포된 원격 NotEditor 웹앱을 연다. 같은 웹 화면과 브라우저
업로드·다운로드 흐름을 사용하면서도 파일 처리와 임시 저장이 사용자 PC 안에서만 이루어지는 실행
경로가 없다. 기존 데스크톱 앱은 로컬 엔진을 쓰지만 pywebview 브리지와 네이티브 파일 대화상자를
사용하므로 사용자가 원하는 웹 실행 형식과는 다르다.

## 목표

Windows 설치 시 `NotEditor 로컬 웹` 바로가기를 추가한다. 이 바로가기는 루프백 전용 NotEditor 웹
서버를 백그라운드에서 시작하고 Edge 또는 Chrome의 독립 앱 모드 창으로 로컬 주소를 연다. 화면과
파일 처리 계약은 배포 웹앱과 같지만 업로드·변환·다운로드는 모두 로컬 프로세스에서 수행한다.
기존 `NotEditor` 데스크톱 바로가기와 사용자가 설치한 원격 PWA는 변경하거나 제거하지 않는다.

## 성공 기준

- [x] 소스 설치와 Inno Setup 설치 모두 `NotEditor 로컬 웹` 시작 메뉴 바로가기를 만들고, 선택한 경우
  바탕화면 바로가기도 만든다.
- [x] 바로가기를 실행하면 콘솔 창 없이 `127.0.0.1`에만 서버가 열리고, 준비가 끝난 뒤 브라우저 앱
  모드 창이 로컬 주소를 표시한다.
- [x] 로컬 웹 창은 pywebview 브리지가 아니라 웹 세션 API를 사용하며 파일 선택은 브라우저 업로드,
  결과 저장은 브라우저 다운로드로 동작한다.
- [x] 같은 바로가기를 다시 실행하면 이미 정상 실행 중인 로컬 NotEditor 서버를 재사용하고 포트 충돌
  오류나 중복 서버를 만들지 않는다.
- [x] 전용 포트를 다른 프로그램이 사용 중이면 그 서비스를 NotEditor로 오인하지 않고 사용자가
  해결할 수 있는 오류와 진단 로그를 남긴다.
- [x] 전용 앱 모드 브라우저 프로세스를 닫으면 실행기가 서버를 정상 종료한다. 이미 실행 중인 서버를
  재사용한 보조 실행기는 서버 소유권을 빼앗거나 종료하지 않는다.
- [x] 기존 데스크톱 `NotEditor` 실행, 원격 웹 배포, Docker 실행 계약을 변경하지 않는다.
- [x] 실행기 단위 테스트, 설치 파일 정적 계약, 전체 회귀 테스트와 실제 Edge 로컬 실행 검사가
  통과한다.

## 범위 밖

- 이미 설치된 원격 PWA를 자동 삭제하거나 그 바로가기를 로컬 주소로 바꾸는 일.
- 외부 기기에서 로컬 서버에 접속하도록 LAN 주소에 바인드하거나 방화벽 규칙을 추가하는 일.
- Windows 외 운영체제용 바로가기·앱 번들 제작.
- 로컬 서버를 Windows 서비스나 부팅 시 자동 시작 프로그램으로 등록하는 일.
- 사용자 문서를 영구 보관하는 데이터베이스 도입.

## 제약

- 서버는 반드시 `127.0.0.1`에만 바인드한다. 로그인 없는 업로드 API를 LAN에 노출하면 같은 네트워크의
  다른 사용자가 로컬 파일 처리 자원을 사용할 수 있기 때문이다.
- 로컬 웹은 배포 웹과 같은 `noteditor.web` 앱과 세션 격리·임시 파일 정리 규칙을 사용한다. 별도 UI
  복사본을 만들면 두 화면의 동작이 다시 갈라지기 때문이다.
- 앱 모드 브라우저에는 `%LOCALAPPDATA%\NotEditor` 아래의 안정적인 전용 프로필을 사용한다. 일반
  브라우저 프로필과 충돌하지 않으면서 서비스 워커와 창 상태를 재사용하기 위해서다.
- 기본 전용 포트는 고정한다. 설치형 로컬 웹의 origin이 매번 달라지면 PWA 캐시와 브라우저 권한이
  유지되지 않기 때문이다.
- 원본 PDF·SDOCX·Notewise는 기존과 같이 읽기 전용으로 취급하고 결과는 새 다운로드로만 만든다.

## 고려했다가 안 한 것

| 대안 | 왜 안 했나 |
|---|---|
| 원격 PWA 바로가기의 주소만 localhost로 변경 | 서버가 먼저 실행되지 않으며 기존 원격 앱을 사용하려는 경로도 사라진다. |
| 기존 pywebview 데스크톱 앱을 로컬 웹이라고 이름만 변경 | 네이티브 브리지와 파일 대화상자를 사용하므로 사용자가 요청한 웹 실행 형식이 아니다. |
| `0.0.0.0:8000` 개발 서버를 바로가기에서 실행 | LAN 노출 위험이 있고 개발 서버·Docker와 포트 충돌하기 쉽다. |
| 실행할 때마다 임의 포트 선택 | 브라우저 origin과 서비스 워커·권한 상태가 매번 달라진다. |
| 서버를 Windows 서비스로 상시 실행 | 설치 권한·업데이트·정리 범위가 커지고 사용하지 않을 때도 프로세스가 남는다. |

## 검증 결과

- PyInstaller 산출물에 기존 `NotEditor.exe`와 별도 `NotEditorLocalWeb.exe`가 함께 생성됐다.
- 실제 Edge 앱 모드 명령줄, `127.0.0.1:8765` 단독 바인드, `/api/health`의 `local-web` 식별자를
  확인했다. 두 번째 실행은 같은 서버 PID를 재사용했고 앱 창 종료 뒤 서버와 실행기가 함께 종료됐다.
- Edge를 우선하고 Chrome을 다음으로 탐색한다. 둘 다 없으면 임의 기본 브라우저로 서버를 남기지
  않고 진단 로그 경로와 함께 명시적으로 실패한다.
- 이 PC에는 Inno Setup 컴파일러가 없어 설치 EXE 자체는 만들지 못했으며, `.iss` 바로가기 계약과
  PyInstaller 번들은 자동 테스트로 검증했다.

## 변경 이력

- 2026-08-30: 사용자가 원격 배포 PWA와 별개로 동일한 웹 형식의 로컬 실행 바로가기를 요청해
  독립 실행기·루프백 서버·브라우저 앱 모드 계약을 확정했다.
- 2026-08-31: 소스·Inno 바로가기, 전용 실행기, 루프백 서버 수명주기와 진단 로그를 구현했다.
  183개 회귀 테스트, PyInstaller 이중 실행 파일 빌드와 실제 Edge 실행·재사용·종료 검사를 통과했다.
