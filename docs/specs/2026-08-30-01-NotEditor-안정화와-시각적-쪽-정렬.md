# NotEditor 안정화와 시각적 쪽 정렬

**날짜:** 2026-08-30
**상태:** 진행 중

## 왜 하는가

배포된 웹앱에서 여러 PDF를 문서 합치기에 올리면 왼쪽 썸네일, 중앙 고해상도 미리보기,
오른쪽 결과 썸네일 요청이 한꺼번에 발생한다. 일부 중앙 미리보기는 처음에 실패했다가 늦게
나타나고, 업로드 뒤 HTTP 502 오류가 수십 개 표시되며, 오른쪽 미리보기는 끝내 나타나지 않는
경우도 있다. 결과 PDF 다운로드 자체는 정상이라 문서 조합보다 미리보기 생성과 요청량 제어가
주된 문제로 보이지만, 실제 운영 로그와 문제 파일로는 아직 확인하지 않았다.

필기 옮기기는 두 번째 파일을 올린 뒤 업로드와 전체 문서 분석을 한 응답 안에서 수행한다. 분석이
길어지는 동안 서버 헬스체크가 5초 안에 응답하지 못했다는 장애 알림이 왔고, 이후 화면에서 먼저
올린 파일과 나중에 올린 파일이 번갈아 사라졌다. 서버 재시작 시 메모리 세션과 임시 파일이 함께
사라졌을 가능성이 있으나 이것도 실물 SDOCX와 운영 로그로는 미확인이다. 사용자는 지금 무엇을
기다리는지 알 수 없고, 실패하면 같은 파일을 여러 번 다시 고르게 된다.

기존 쪽 매칭 확인 화면은 번호 선택표와 한 장짜리 겹침 미리보기가 분리돼 있어 자동 대응 관계를
눈으로 이해하고 고치기 어렵다. 휠을 한 번 움직일 때마다 다음 한 장을 불러오며, 로딩이 끝나기
전에는 계속 이동할 수 없다. 결과적으로 많은 쪽을 연속해서 검토하기 어렵고 불확실한 쪽을 놓치기
쉽다.

## 목표

작업을 세 단계로 나눈다. 1차에서는 문서 합치기와 필기 옮기기의 서버 과부하·세션 유실 가능성을
줄이고, 업로드와 분석 단계를 구분해 보여 주며, 저장 이름과 초기화 버튼을 정돈한다. 2차에서는
기존 쪽 매칭 표와 한 장짜리 정렬 미리보기를 하나의 연속 스크롤 좌우 비교 화면으로 바꾼다. 옛
파일은 왼쪽에 고정하고 새 PDF 쪽은 오른쪽에서 드래그해 행을 바꾸며, 옮긴 위치의 옛 쪽과 새로
대응하고 결과 쪽 순서도 그 행 순서를 따른다. 3차에서는 Goodnotes와 Flexcil의 편집 가능한 필기
보존 가능성만 조사하고, 구현 여부는 별도 결정한다.

자동 매칭은 기존의 순서 보존 방식을 기본값으로 유지한다. 사용자가 경고를 확인하고 직접 드래그한
경우에만 이 전제를 벗어날 수 있다. 2026-08-26 쪽 매칭 명세의 "공통 쪽 순서 변경은 범위 밖"이라는
제약은 **자동 매칭에 대해서는 계속 유효**하지만, 이 명세에서 정의하는 확인된 수동 수정에는 더
이상 적용하지 않는다.

## 확정된 단계와 동작

### 1차 — 성능·안정성 및 기본 UI

- 화면에 가까운 쪽만 미리보기를 요청하고, 썸네일과 고해상도 미리보기의 동시 생성 수를 제한한다.
- 같은 쪽·같은 크기의 진행 중 요청은 하나로 합친다. 화면에서 멀어진 요청은 취소하거나 결과를
  버리며, 브라우저와 서버의 이미지 캐시는 페이지 수에 비례해 끝없이 커지지 않게 상한을 둔다.
- 개별 미리보기 실패를 전역 토스트 수십 개로 쏟지 않는다. 해당 쪽 안에 실패 상태와 다시 시도
  동작을 표시하고, 일시적인 502에는 제한된 횟수만 자동 재시도한다. 업로드·저장 같은 POST 요청은
  자동 재전송하지 않는다.
- 가벼운 헬스체크는 미리보기·매칭 작업 대기열과 분리한다. 미리보기 부하 중에도 헬스체크가 서버
  장애로 오인될 만큼 오래 막히지 않아야 한다.
- 필기 파일 수신과 전체 분석을 한 상태로 뭉치지 않는다. 최소 파일 검증을 통과한 업로드는 먼저
  선택 상태로 확정하고, 그다음 구조 확인·쪽 지문 계산·자동 매칭·좌표 정렬·미리보기 준비를 별도
  작업 단계로 진행한다.
- 새 업로드가 중단되거나 검증에 실패하면 해당 칸의 직전 정상 파일을 유지한다. 분석 실패 뒤에도
  이미 정상 업로드된 두 파일을 유지하고 재분석할 수 있어야 한다. 단, Render 프로세스 자체가
  재시작되면 임시 작업공간을 복구하는 영구 저장소까지 이번 범위에서 만들지는 않는다.
- 로딩 문구는 최소한 `파일 업로드 중`, `파일 구조 확인 중`, `페이지 비교·자동 매칭 중`,
  `필기 좌표 정렬 중`, `미리보기 준비 중`을 구분한다. 웹에서 업로드 진행률을 얻을 수 있으면
  백분율도 표시한다.
- 문서 합치기와 필기 옮기기 모두 저장 버튼 가까이에 편집 가능한 파일명 입력란을 둔다. 확장자는
  결과 형식에 맞게 고정하고, 금지 문자는 기존 서버 규칙으로 정리한다. 문서 합치기의 기본값은
  첫 원본 이름을 기준으로 한 `원본명-편집본.pdf`, 필기 옮기기는
  `대상PDF명-필기.sdocx` 또는 `대상PDF명-필기.notewise`로 한다.
- `문서 비우기`와 `선택 초기화`는 같은 시각적 계층, 크기, 아이콘·문구 규칙을 사용한다. 각 버튼은
  자기 도구의 파일만 지운다는 설명을 유지하고, 파일이 있을 때 쉽게 찾을 수 있어야 한다.

### 2차 — 연속 스크롤 좌우 비교와 수동 정렬

- 기존 `쪽 매칭 확인` 선택표와 한 장짜리 `정렬 확인` 화면을 하나의 좌우 비교 화면으로 통합한다.
  상단에는 전체 쪽 수, 자동 연결 수, 새 파일 전용 수, 옛 파일 전용 수, 확인 필요 수만 간단히
  표시한다.
- 각 행은 옛 파일 쪽을 왼쪽, 새 PDF 쪽을 오른쪽에 둔다. 자동 매칭된 두 쪽은 같은 행에 놓는다.
  옛 파일에만 있는 쪽은 오른쪽을 비우고, 새 PDF에만 있는 쪽은 왼쪽을 비운다.
- 기본 확대율에서 새 PDF 쪽 약 3장이 한 화면에 보이는 높이를 사용한다. 일반 스크롤처럼 부드럽게
  계속 내려갈 수 있어야 하며, 이미지 로딩이 다음 행 이동을 막지 않는다. 화면 밖 이미지는 지연
  로딩하고 자리·쪽 번호·상태 표시는 즉시 그린다.
- 옛 파일 열은 고정한다. 새 PDF 쪽은 세로 드래그로 다른 행으로 이동할 수 있다. 이동하면 새 PDF
  쪽 순서가 실제 결과 순서로 바뀌고, 도착한 행의 옛 파일 쪽과 새 대응 관계가 된다. 중간 행에서
  밀린 새 PDF 쪽들도 각자 새 위치의 옛 쪽과 대응한다.
- 드래그 적용 전에 기존 자동·수동 대응 중 몇 개가 바뀌는지와 영향을 받는 쪽 번호를 경고한다.
  사용자가 취소하면 아무 상태도 바꾸지 않는다. 계속하면 영향을 받은 모든 행을 `확인 필요`로
  바꾼다.
- 자동 매칭 신뢰도가 낮은 행, 옛 파일 또는 새 파일 한쪽만 있는 행, 사용자가 대응을 바꾼 행은
  눈에 띄게 하이라이트한다. 각 행 옆에 `확인` 버튼을 두며, 확인 여부는 페이지 이동과 미리보기
  재로딩 뒤에도 유지한다.
- `필기 보기` 토글로 실제 필기·형광펜 오버레이를 켜고 끌 수 있다. 켜면 대응된 옛 배경과 새 배경
  양쪽에서 같은 필기 위치를 비교할 수 있다. 미리보기에서 해석하지 못한 객체도 저장 결과에서는
  기존처럼 원시 데이터를 보존한다.
- 확인이 필요한 행이 남은 상태에서 `옮기기`를 누르면 남은 개수와 쪽 번호를 보여 주고 정말
  진행할지 한 번 더 묻는다. 사용자가 명시적으로 진행하면 저장을 허용하되 결과 경고에도 미확인
  쪽을 기록한다.
- 결과는 화면의 행 순서를 따른다. 양쪽이 있는 행은 새 배경과 옛 필기를 결합한다. 새 파일에만
  있는 행은 빈 필기 페이지를 만들고, 필기가 있는 옛 파일 전용 행은 옛 배경과 필기를 함께
  보존한다. 형식상 필요한 비-PDF 호환 페이지는 화면 행에서 숨기고 기존 보존 규칙을 지킨다.
- Samsung Notes와 Notewise가 같은 행 기반 수정 계약을 사용한다. 특정 형식에서 사용자가 확정한
  재정렬이나 옛 파일 전용 필기 보존을 안전하게 만들 수 없다면 조용히 누락하지 말고 저장 전에
  그 형식과 이유를 명확히 거부한다.

### 3차 — Goodnotes·Flexcil 조사

- 각 앱이 내보내고 다시 가져올 수 있는 원본 형식, 편집 가능한 펜 데이터 위치, 페이지 대응 정보,
  배경 PDF 교체·재정렬 가능성, 알려지지 않은 데이터의 바이트 보존 가능성을 조사한다.
- PDF 주석으로 평탄화된 결과를 옮기는 것은 "편집 가능한 필기 옮기기 지원"으로 간주하지 않는다.
- 실제 샘플 없이 구현하지 않는다. 조사 결과는 형식별 `지원 가능`, `추가 샘플 필요`, `안전하게
  지원 불가` 중 하나와 근거를 남기고 별도 승인을 받는다.

## 성공 기준

### 1차

- [ ] 합성 PDF 3개, 각 100쪽을 한 번에 등록해도 브라우저가 모든 쪽의 썸네일·고해상도 이미지를
  동시에 요청하지 않으며 동시 처리 상한을 자동 테스트로 확인한다.
- [ ] 같은 이미지의 동시 요청은 실제 렌더 한 번으로 합쳐지고, 미리보기 캐시는 정한 개수 또는
  바이트 상한을 넘으면 오래된 항목부터 비운다.
- [ ] 합성 부하 테스트 중 `/api/health`가 1초 안에 응답하고 5초 타임아웃이 발생하지 않는다.
- [ ] 일시적 미리보기 실패는 해당 페이지에서 재시도할 수 있고, 동일 장애가 전역 오류 알림으로
  반복 표시되지 않는다.
- [ ] 첫 번째 필기 파일이 선택된 상태에서 두 번째 파일 업로드 또는 분석이 실패해도 첫 번째 파일이
  사라지지 않는다. 두 파일 분석 실패 뒤 재분석도 재업로드 없이 가능하다.
- [ ] 업로드, 구조 확인, 페이지 비교·자동 매칭, 좌표 정렬, 미리보기 준비가 서로 다른 상태로
  표시된다.
- [ ] 문서 합치기와 필기 옮기기에서 사용자가 파일명을 수정할 수 있고, 웹 다운로드와 데스크톱
  저장 창 모두 수정한 이름과 올바른 확장자를 사용한다.
- [ ] `문서 비우기`와 `선택 초기화`가 같은 버튼 체계를 사용하면서 다른 도구의 파일은 지우지 않는다.
- [ ] 기존 단위·HTTP·정적 UI 테스트와 새 성능·상태 전이 테스트가 모두 통과한다.

### 2차

- [ ] 자동 매칭 결과가 옛 파일 왼쪽·새 파일 오른쪽의 행으로 표시되고, 한쪽 전용 쪽도 빈 칸과 함께
  올바른 위치에 나타난다.
- [ ] 기본 화면에 새 PDF 약 3쪽이 보이고, 100쪽 합성 문서에서도 로딩 완료를 기다리지 않고 연속
  스크롤할 수 있다.
- [ ] 새 PDF 쪽 드래그 전 영향 관계 경고가 나오며, 취소 시 무변경, 진행 시 결과 순서·대응 관계와
  확인 상태가 정해진 규칙대로 바뀐다.
- [ ] 불확실·한쪽 전용·수동 변경 행이 강조되고 각 행을 개별 확인할 수 있다.
- [ ] 필기 보기 토글이 실제 필기 오버레이만 바꾸며 저장 데이터에는 영향을 주지 않는다.
- [ ] 미확인 행이 남은 저장에는 최종 경고가 나오고, 사용자가 취소하거나 명시적으로 계속할 수 있다.
- [ ] 대상 순서 변경, 옛 파일 전용 필기 쪽, 새 파일 전용 쪽을 섞은 합성 사례가 Samsung Notes와
  Notewise 결과 계약을 만족한다. 안전하게 만들 수 없는 형식은 저장 전에 명시적으로 거부한다.
- [ ] 원본 SDOCX, Notewise, 대상 PDF를 덮어쓰지 않고 항상 새 결과 파일을 만든다.

### 3차

- [ ] Goodnotes와 Flexcil 각각에 대해 지원 가능성 표와 근거, 필요한 실제 샘플 목록을 남긴다.
- [ ] 편집 가능한 필기 보존이 검증되지 않은 형식을 지원한다고 UI나 문서에서 약속하지 않는다.

## 범위 밖

- 이번 명세 작성 단계에서 제품 코드, 테스트, 배포 설정을 수정하거나 운영 서버에 배포하는 일.
- 실물 SDOCX·Notewise·오창모 PDF에서 문제가 해결됐다고 주장하는 일. 사용자는 이번에는 합성
  파일로 먼저 진행하기로 했고 실물 검증은 뒤로 미뤘다.
- Render 프로세스 재시작 뒤에도 업로드를 복구하는 영구 파일 저장소·데이터베이스 도입.
- 필기 획 좌표를 재계산하거나 다시 직렬화하는 방식. 배경과 페이지 대응을 바꾸되 기존 필기 원시
  바이트 보존 원칙은 유지한다.
- Goodnotes·Flexcil 지원 구현. 3차는 조사와 별도 의사결정까지만 한다.
- 이번 작업과 무관한 배포 주소, 도메인, 계정, 모니터링 서비스 변경.

## 제약

- 원본 SDOCX, Notewise, 대상 PDF는 절대 덮어쓰거나 삭제하지 않는다. 사용자가 명시적으로 초기화한
  웹 임시 업로드 사본만 지울 수 있다.
- Samsung Notes의 필기 `.page`와 Notewise에서 의미를 모르는 protobuf 필드는 재직렬화로
  정규화하지 않고 기존 형식별 바이트 보존 규칙을 지킨다. 미리보기 해석 범위와 저장 보존 범위를
  혼동하면 화면에 안 보이는 객체가 사라질 수 있기 때문이다.
- 자동 매칭은 순서 보존 DP와 현재 쪽 지문을 유지한다. 거의 같은 슬라이드는 화면 생김새만으로
  정확히 구분하기 어려워 순서가 자동 정확도의 핵심 근거다. 순서 전제를 깨는 것은 경고를 확인한
  수동 드래그에만 허용한다.
- 오창모 PDF 가능성 검토는 PDF 내부 객체나 텍스트 추출 순서가 아니라 **렌더링되어 실제로 보이는
  페이지 영역**으로 지문을 계산하는 방향을 유지한다. 현재 구현도 본문 영역을 렌더링해 고정 격자
  지문을 만들지만, 실제 파일이 없으므로 해결 여부는 미확인이다.
- 미리보기 최적화 때문에 저장본을 래스터 이미지로 바꾸지 않는다. 문서 합치기 저장본은 계속 원본
  PDF 객체를 사용한다.
- UI와 서버가 주고받는 수동 계획은 각 사용자 쪽과 대상 쪽을 최대 한 번만 포함해야 한다. 빈 행은
  허용하지 않으며, 범위 밖 번호·중복 쪽·클라이언트에 없던 쪽은 서버가 다시 검증해 거부한다.
- 운영 환경이 작은 인스턴스라는 가정으로 동시성을 제한하되 정확한 상한은 합성 부하 측정으로
  정한다. 빠른 개발 PC 기준만으로 값을 고정하지 않는다.

## 고려했다가 안 한 것

| 대안 | 왜 안 했나 |
|---|---|
| 모든 수정과 Goodnotes·Flexcil 지원을 한 번에 구현 | 장애 원인과 대규모 정렬 UI, 미확인 파일 형식이 섞이면 검증 범위가 너무 커진다. 사용자가 1차 안정화 → 2차 UI → 3차 조사를 선택했다. |
| 기존 한 장 미리보기에 다음 쪽 선로딩만 추가 | 로딩 대기는 조금 줄지만 좌우 대응 전체를 연속해서 검토하고 수동으로 고치는 목표를 충족하지 못한다. |
| 새 PDF를 드래그해도 기존 필기 대응을 페이지에 붙여 유지 | 사용자는 새 쪽을 옮긴 행의 옛 쪽과 다시 대응하고 결과 순서도 바뀌는 동작을 선택했다. |
| 수동 변경에서도 원본 순서 보존을 강제 | 현재 UI와 서버의 제약이지만, 사용자가 잘못된 자동 대응과 새 PDF 순서를 직접 고칠 수 없게 된다. 자동은 순서를 지키고 수동 변경만 경고 후 허용한다. |
| 미확인 행이 하나라도 있으면 저장을 완전히 금지 | 사용자는 경고 후 정말 진행할지 선택할 수 있기를 원했다. 명시적 재확인을 거치면 허용하고 결과 경고를 남긴다. |
| 모든 미리보기를 업로드 직후 미리 생성 | 작은 문서는 빨라 보일 수 있지만 큰 문서에서 CPU·메모리·요청 폭주를 다시 만든다. 화면 근처 우선 생성과 제한된 캐시를 사용한다. |
| 실패한 미리보기·업로드 요청을 모두 자동 재시도 | POST 재전송은 중복 등록이나 상태 덮어쓰기를 만들 수 있다. 멱등인 미리보기 요청만 제한적으로 재시도한다. |
| 서버 재시작 복구를 위해 즉시 영구 저장소 도입 | 이번 장애를 줄이는 데 비해 운영·개인정보·정리 정책 범위가 크게 늘어난다. 먼저 과부하와 상태 전이를 고친다. |
| PDF로 보이는 필기를 Goodnotes·Flexcil 지원으로 선언 | 평탄화된 PDF 주석은 원래 앱에서 편집 가능한 펜 데이터 보존을 증명하지 못한다. |

## 열린 질문

- 미리보기 동시성·캐시의 최종 기본값. 합성 3×100쪽 부하와 작은 운영 인스턴스 조건을 재현해
  측정한 뒤 정한다.
- 실제 502가 미리보기 요청 폭주 때문인지, Render 재시작이 필기 파일 선택 유실의 직접 원인인지.
  운영 로그와 실물 파일 검증 전까지는 가설이다.
- 오창모 PDF에서 현재의 보이는 본문 기반 지문이 안정적으로 쪽을 구분하는지. 합성 테스트는 유사
  슬라이드·빈 쪽·스캔 쪽·여백 변화·순서 변경을 포함하되, 최종 판단에는 실제 PDF가 필요하다.
- 수동 재정렬과 옛 파일 전용 필기 보존을 실제 Samsung Notes 및 Notewise 앱이 모두 받아들이는지.
  PC 구조 검증 뒤 기기·앱 검증이 별도로 필요하다.
- Goodnotes와 Flexcil의 실제 원본 내보내기 샘플을 언제 확보할 수 있는지.

## 변경 이력

- 2026-08-30: 사용자 테스트 결과를 바탕으로 1차 안정화, 2차 좌우 정렬 UI, 3차 형식 조사 순서를
  확정했다. 새 PDF 드래그는 도착 행의 옛 쪽과 재대응하고 결과 순서도 바꾸며, 실물 파일 없이
  합성 테스트로 먼저 진행하고 이번 범위는 명세 작성까지로 정했다.
