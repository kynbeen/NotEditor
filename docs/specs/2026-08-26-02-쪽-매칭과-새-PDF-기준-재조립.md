# 쪽 매칭과 새 PDF 기준 재조립

**날짜:** 2026-08-26
**상태:** 진행 중

## 왜 하는가

지금의 필기 이전은 두 문서의 **쪽수가 같고 순서도 같아야** 동작한다. 실제로는 개정판 PDF에
슬라이드가 추가되거나 빠진다. 게다가 결과 문서가 원본 `.sdocx`의 페이지 구성을 그대로 따르기
때문에, 새 PDF에 추가된 쪽은 결과에서 **사라진다**. 개정판을 받을 때마다 필기를 옮기려는 것이
이 기능의 목적인데, 정작 개정에서 가장 흔한 변화(쪽 추가·삭제)를 못 다룬다.

## 목표

필기가 든 `.sdocx`와 쪽이 추가·삭제된 새 PDF를 받아, 두 문서에 공통으로 있는 쪽을 **순서를
지키면서** 자동으로 짝짓고, 필기를 짝지어진 쪽으로 옮긴다. 결과 문서는 **새 PDF의 모든 쪽**을
담는다. 필기 좌표는 다시 계산하지 않고, PDF 쪽 크기를 필기 캔버스에 맞춘다.

## 성공 기준

- [ ] 배율·여백 변화에 흔들리지 않는 쪽 지문(본문 상자를 고정 격자로 정규화)으로 두 문서의 쪽을 비교한다.
- [ ] 순서 보존 정렬(Needleman-Wunsch식 DP)로 양쪽의 삽입·삭제를 갭으로 처리해 공통 쪽을 짝짓는다.
- [ ] 결과 문서에 새 PDF의 모든 쪽이 들어간다.
- [ ] 짝지어진 쪽은 옛 `.page`를 **바이트 단위로 복사**한다. 필기·형광펜은 재직렬화하지 않는다.
- [ ] 새 PDF에만 있는 쪽은 원본에 이미 있는 빈 `.page`를 복제하고 UUID와 32바이트 해시만 새로 준다.
- [ ] 옛 파일에만 있는 **필기 쪽**은 그 옛 배경 페이지를 결과 PDF에 끼워 넣어 함께 유지한다. 필기를 버리지 않는다.
- [ ] `pageIdInfo.dat`를 새 쪽 구성으로 다시 쓴다. 각 쪽의 32바이트 블록은 해당 `.page` 안에서 읽어 옮긴다.
- [ ] `note.note`의 `height`를 `Σ(페이지 높이) + 세로여백 × (쪽수−1)`로 갱신한다.
- [ ] EOCD 뒤 148바이트 Samsung 꼬리표와 ZIP 엔트리 헤더 규칙을 재조립 경로에서도 지킨다.
- [ ] 쪽수와 구성이 그대로면 기존 바이트 보존 경로를 쓰고, 삽입·삭제가 있을 때만 재조립 경로로 넘어간다(자동 선택).
- [ ] 매칭 결과를 미리보기로 렌더링해 보여주고, 사람이 짝을 수동으로 고칠 수 있다.
- [ ] 결과 파일이 태블릿의 Samsung Notes에서 열린다. **기기에서만 확인 가능.**

## 범위 밖

- 공통 쪽의 **순서가 바뀌는** 경우. 사용자가 일어나지 않는다고 확정했고, 이 조건이 매칭 정확도를 만든다.
- 쪽마다 다른 배율. 배율은 문서 전체에 하나만 쓴다.
- 필기 획 좌표의 재계산·재직렬화.
- `.spi` 렌더 캐시 재생성. 원본 것을 그대로 옮긴다.
- 내장 PDF가 둘 이상인 문서.
- 두 문서의 쪽을 사람이 처음부터 손으로 짝짓는 기능(자동 결과의 수정만 지원).

## 제약

- **필기가 든 `.page`는 바이트 단위로 복사한다.** 획의 점이 가변길이 델타로 패킹돼 있고 참고한
  역공학 문서도 stroke width/material 알고리즘은 미확정이라고 적고 있다. 재직렬화하면 조용히 깨진다.
- **ZIP을 다시 포장하지 않는다.** 1차에서 확인했듯 EOCD 뒤 꼬리표가 사라지면 Samsung Notes가
  파일을 열지 못한다. 재조립 경로도 같은 규칙(로컬 헤더·중앙 디렉터리·플래그 비트 보존)을 따른다.
- **32바이트 페이지 해시는 알고리즘을 모른다.** 그 값이 `.page` 파일 끝에서 58바이트 위치에
  들어 있음을 실제 파일 51/51쪽에서 확인했다. **읽어서 옮기기만 하고 계산하지 않는다.**
- 원본 `.sdocx`와 PDF는 수정하지 않는다. 출력 경로가 원본이면 거부한다.

## 고려했다가 안 한 것

| 대안 | 왜 안 했나 |
|---|---|
| 필기 획 좌표를 변환해 새 캔버스에 맞추기 | 가변길이 델타 패킹이라 `.page` 전체 재직렬화가 필요하고, stroke width 알고리즘이 미확정이다. 바이트 보존 성질도 잃는다. |
| `.page`의 `pdfDataList` rect만 패치해 배경 위치를 옮기기 | 1·2차에서는 배경 PDF를 다시 그리는 것으로 충분했다. 3차는 쪽 추가·삭제 때문에 어차피 페이지 목록을 다시 써야 하므로 이 경로만으로는 부족하다. 결과 문서를 새 PDF의 실제 쪽 크기로 만들고 싶어지면 다시 꺼낼 수 있는 수단이다. |
| 새 PDF에만 있는 쪽을 결과에서 빼고 알리기 | 사용자가 "새 PDF의 모든 페이지는 보존되어야 한다"고 확정했다. |
| 옛 파일에만 있는 필기 쪽을 버리기 | 필기가 사라진다. 옛 배경 페이지를 결과 PDF에 끼워 넣으면 아무것도 잃지 않는다. |
| Dietrich 파서로 문서를 왕복시켜 다시 쓰기 | 필기 데이터가 제3자 파서를 왕복하면서 바이트 보존이 깨진다. 포맷 지식과 문서만 참고하고 코드는 자체 구현한다. |
| 기존 바이트 보존 경로를 폐기하고 재조립으로 일원화 | 쪽 구성이 그대로인 흔한 경우까지 위험을 올린다. 자동 선택으로 둘 다 유지한다. |
| 지문만으로 가장 닮은 쪽 고르기(greedy) | 실제 샘플에서 27·28쪽이 쌍둥이라 1등과 2등의 격차가 0.0024까지 좁아졌다. 순서 보존 DP가 이 애매함을 위치로 해소한다. |

## 열린 질문

- 매칭을 '확신 없음'으로 표시할 지문 거리 기준값. 실제 문서로 정해야 한다.
- 수동 수정 UI의 형태(표에서 짝 바꾸기 / 쪽마다 대상 고르기).
- `note.note`의 `last edited page index`가 새 쪽수를 넘을 때 클램프가 필요한지. **미확인.**
- 재조립 경로로 만든 문서를 태블릿에서 열어본 적이 없다. **경로 전체가 기기 미검증.**
- 매칭에 실패했을 때(공통 쪽을 거의 못 찾음) 거부할지, 사람에게 넘길지.

## 변경 이력

- 2026-08-26: 최초 작성. 쪽 지문·순서 보존 DP·문서 재조립의 실현 가능성을 실제 샘플로 확인한 뒤 범위를 확정했다.
