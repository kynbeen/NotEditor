# 쪽 제외 머지와 실기 검증 세트 인계

**날짜:** 2026-09-02
**기기:** LAPTOP
**관련 명세:** `docs/specs/2026-09-02-01-PDF-기준-필기-페이지-비율.md`
**직전 인계:** `docs/handoffs/2026-09-02-01-PDF-기준-필기-비율-수정.md`

## 현재 상태

PR #3(쪽 제외)을 **고쳐서 머지**했다 — 그대로 머지했으면 기능이 동작하지 않았다. 실제
Samsung Notes·Notewise·Goodnotes 파일로 비율 검증 세트를 만들어 결과 파일과 대조 그림을
`tmp/실기검증/` 에 남겼다. SDOCX 와 Notewise 는 필기가 정확히 따라갔고, Goodnotes 는 자료
하나에서 어긋났는데 원인이 형식이 아니라 **정렬 추정 품질**임을 다른 자료로 확인했다. 앱으로
가져오는 마지막 확인만 남았다. `main` 은 `4d11f43`, 전체 테스트 **241개 통과**.

## 이번 세션에 한 일

### PR 검토 — devkit 경로는 쓸 수 없었다

`review.py list` 는 `config.json` 이 이 기기에 없고(예시 파일만 있다), 두 PR 이 백로그 모듈이
아니라 포크 `DreamSailed` 에서 온 것이라 슬러그 매칭으로는 잡지 못한다. 두 PR 을 직접 봤다.

### PR #3 (쪽 제외) — 고쳐서 머지

- 텍스트 충돌은 없었고 머지 후 테스트도 전부 통과했지만, **웹 저장 경로에 실제로 제외 행을
  넣으면 HTTP 400** 이 났다: `쪽 대응 계획은 원본 PDF의 모든 쪽을 한 번씩 담아야 합니다.`
- 원인은 `sdocx_rebuild._validate_match` 가 모든 원본·대상 쪽의 포함을 요구하는 것이다.
  **비율 수정 탓이 아니다** — PR 자기 베이스(`68f1bf1`)에서 비율 변화 없는 `exact` 모드로도
  같은 400 이 났다. PR 의 테스트가 `PagePlan.from_payload` 단위에서 멈춰 못 잡았다.
- `_validate_match` 가 사용자가 선언한 제외 쪽을 함께 세도록 고쳤다. Notewise·Goodnotes 는
  계획 슬롯으로 출력을 구성해 이미 통과했다(실측 확인).
- 종단 회귀 검사를 붙였다: 비율이 바뀐 대상에서 SDOCX 제외 저장, Notewise 제외 저장,
  그리고 재조립 층에서 "빠진 쪽"과 "뺀 쪽"을 가르는 한 쌍.

### PR #2 (Goodnotes 목차) — 보류

`goodnotes_transfer.py`, `tests/test_web.py` 충돌. PR 이 `9b1535e` 이전 코드 기준이라
`ink_transform.canvas_transform`, `transform_goodnotes_journal`, `alignment_for_plan` import 와
대상 PDF 바이트 보존 경로를 통째로 지운다. **그대로 머지하면 비율 수정이 되돌아간다.**
사용자 판단으로 지금은 손대지 않았다. GitHub 에 코멘트도 남기지 않았다.

### 실기 검증 세트

- Downloads 에 실제 샘플이 있었다(직전 인계의 "샘플 없음"은 틀렸다). `.sdocx` 29개,
  `.notewise` 3개, `.goodnotes` 4개.
- `tools/make_ratio_check_set.py` 가 원본의 배경 PDF 를 꺼내 **세로 30% 늘린 페이지 상자**에
  담은 대상 PDF 를 만들고 필기를 옮긴다. 원본은 읽기만 한다.
- `tools/render_ratio_check_pages.py` 가 각 파일을 자기 배경에 대고 미리보기해 옮기기 전후
  같은 쪽을 PNG 로 뽑는다. 태블릿 없이도 위치를 눈으로 볼 수 있다.
- 결과: 960x540 → 960x702, 세 형식 모두 저장 성공, 획 수 보존
  (SDOCX 95쪽, Notewise 170획, Goodnotes 1053획).

## 내린 결정과 근거

- **`_validate_match` 를 느슨하게 풀지 않고 제외 목록을 받게 했다.** "빠졌다"와 "빼기로 했다"를
  구분하지 못하면 조용한 쪽 유실을 잡아 주던 검사가 무의미해진다.
- **PR #3 을 거부하지 않고 고쳐서 머지했다.** 사용자 지시다. 리뷰가 코드를 안 고친다는 devkit
  원칙보다 사용자 결정이 앞선다.
- **대상 PDF 를 `show_pdf_page` 로 다시 그리지 않고 페이지 상자만 늘린다.** 다시 그리면 원본
  쪽이 통째로 XObject 하나가 되어 본문 상자가 쪽 전체로 잡히고, 정렬 추정이 "본문이 줄었다"고
  읽는다. 실제 강의자료는 그렇지 않다.
- **정렬 추정 품질 문제를 임의로 고치지 않았다.** 무엇을 할지(거절/경고/쪽 상자 기준 대체)가
  설계 결정이라 사용자 판단이 필요하다.

## 고려했다가 안 한 것

| 대안 | 왜 안 했나 |
|---|---|
| devkit `config.json` 을 만들어 `review.py list` 를 돌리기 | 이 기기엔 무인 루프가 없고, 포크 PR 은 슬러그 매칭으로 잡히지도 않는다. |
| `_validate_match` 를 "중복 없고 범위 안"으로만 완화 | 사용자가 의도하지 않은 쪽 유실을 못 잡게 된다. |
| PR #2 를 리베이스해서 같이 머지 | 사용자가 보류를 골랐다. |
| 합성 필기 파일로 검증 세트 만들기 | 실제 앱이 가져오지 못해 실기 검증이 성립하지 않는다. |

## 미해결 질문 / 블로커

- **정렬 추정에 절대 품질 기준이 없다.** `transfer_plan.alignment_for_pairs` 는 쪽 크기가
  다를 때 `estimate_alignment` 가 준 값을 **잔차와 무관하게 그대로** 쓴다. `improves` 와
  `axes_agree` 검사는 크기가 같을 때만 적용된다. `병리_이소민 4-2.goodnotes` 에서는 배율
  0.911, 잔차 172.8pt(약 61mm) 인 추정이 그대로 적용되어 필기가 한 줄 위로, 가로로도
  어긋났다. 같은 방식으로 만든 `약리학_1주차(1)...goodnotes` 는 정확히 맞았으니 형식이 아니라
  추정 품질 문제다. SDOCX 는 잔차 30.2mm 로 시각적으로 정확했다 — 쓸 만한 임계값이 무엇인지는
  아직 모른다.
- 세 앱으로 결과를 실제로 가져와 여는 확인은 아직 못 했다. GUI 조작과 태블릿이 필요해 직접
  할 수 없다. 확인 항목은 `tmp/실기검증/읽어주세요.md` 에 적어 두었다.
- PR #2 는 열려 있고 비율 수정과 충돌 상태 그대로다.
