# 쪽 매칭 엔진과 SDOCX 원시 연산

**날짜:** 2026-08-26
**기기:** LAPTOP
**관련 명세:** [docs/specs/2026-08-26-02-쪽-매칭과-새-PDF-기준-재조립.md](../specs/2026-08-26-02-쪽-매칭과-새-PDF-기준-재조립.md)
(1·2차는 [docs/specs/2026-08-26-01-Samsung-Notes-필기-이전.md](../specs/2026-08-26-01-Samsung-Notes-필기-이전.md))

## 현재 상태

3차(쪽 매칭 + 새 PDF 기준 재조립)의 **부품이 다 만들어졌고, 아직 조립되지 않았다.** 쪽을 짝짓는
엔진과, `.page`·`pageIdInfo.dat`·`note.note` 를 필기 데이터를 재직렬화하지 않고 고치는 원시
연산이 각각 완성·검증됐다. 이것들을 묶어 실제로 새 `.sdocx` 를 만들어내는 재조립 코드가 다음 일이다.
1·2차(꼬리표 보존, 본문 기준 정렬)는 완료되어 앱에서 동작한다. 테스트 73개 통과.

## 이번 세션에 한 일

1. **1차 버그 해결** — 결과 `.sdocx` 가 삼성 노트에서 안 열리던 원인이 ZIP 재포장이었다. 진짜 삼성
   파일은 ZIP 종료 기록(EOCD) *뒤에* `Document for S-Pen SDK` 로 끝나는 148바이트 꼬리표를 달고
   있는데, 파이썬 ZIP 라이브러리로 다시 만들면서 그게 사라졌다. 아카이브를 재생성하지 않고 바뀌는
   두 항목만 제자리에서 갈아 끼우는 방식으로 바꿨다.
2. **2차 본문 기준 정렬** — 배율·여백이 달라진 PDF를 원본 페이지 좌표계에 다시 앉힌다
   (`alignment.py`). 앱에 겹쳐보기 미리보기를 붙였고, 숨은 WebView2 창으로 실제 동작을 확인했다.
3. **3차 명세 작성** (`docs/specs/…-02-…md`, 커밋 `491c820`).
4. **쪽 매칭 엔진** (`page_match.py`) — 쪽 지문 + 순서 보존 DP.
5. **SDOCX 원시 연산** (`sdocx_page.py`, `sdocx_note.py`).

## 내린 결정과 근거

- **필기 좌표를 옮기지 않고 배경 쪽을 옮긴다.** `.page` 는 캔버스 좌표(1848×1039)에 획을 저장하고,
  배경 PDF는 `pdfDataList = (fileId, pageIndex, rect)` 라는 페이지 속성으로 그 캔버스에 그려진다.
  둘이 별개 좌표계라 배경만 옮겨도 상대 위치가 맞는다. 획은 가변길이 델타 패킹이라 다시 쓰면 깨진다.
- **32바이트 페이지 해시는 계산하지 않고 옮긴다.** 계산식은 모른다. 그런데 그 값이 `.page` 파일
  끝에서 58바이트 위치에 그대로 들어 있고 `pageIdInfo.dat` 이 같은 값을 들고 있다(실제 파일
  102쪽에서 확인). 복사하면 일관성이 유지되므로 알 필요가 없다.
- **`note.note` 는 높이 u32 하나만 고친다.** 쪽 목록이 없다. 공식
  `height = Σ(캔버스 높이) + 세로여백 × (쪽수−1)` 을 실제 파일 두 개에서 오차 없이 맞췄다
  (56613 = 54563 + 41×50).
- **지문은 셀당 픽셀 하나가 아니라 셀 평균으로 만든다.** 점 추출은 배율이 조금만 달라져도 값이 튄다.
  실측으로 정답 짝 거리 중앙값이 0.375 → 0.069 로 떨어졌고, 47/47 정확 매칭이 됐다.
- **갭 비용 0.35** — 실측 분포(정답 짝 최대 0.22, 오답 최소 0.78)를 보고 "거리가 0.70을 넘으면
  짝짓느니 양쪽에 갭을 둔다"는 뜻이 되게 잡았다.
- **`samples/` 는 커밋하지 않았다.** 실제 필기가 든 개인 파일 40MB다. 테스트는 전부 합성 데이터를
  쓰므로 없어도 돌아간다.

## 고려했다가 안 한 것

| 대안 | 왜 안 했나 |
|---|---|
| 지문을 셀당 픽셀 하나로 뽑기 | 코드는 짧지만 배율 변화에 값이 튄다. 실측에서 재조판 판본의 정답 짝 거리가 0.375까지 벌어지고 한 쪽을 놓쳤다. 셀 평균으로 바꾸니 0.069, 47/47. |
| DP 역추적에서 비용을 부동소수점 동등 비교로 되짚기 | 정방향에서 고른 수를 따로 적어두는 편이 안전하다. 비용 차이가 거의 없다. |
| `samples/` 를 리포에 커밋 | 개인 필기 40MB. 테스트가 의존하지 않는다. |

## 미해결 질문 / 블로커

- **이 리포에는 git 원격이 없다.** 그래서 이 문서는 이 기기(LAPTOP)에만 남는다. 다른 기기로
  넘기려면 원격을 먼저 만들어야 한다.
- **재조립 경로로 만든 문서를 태블릿에서 열어본 적이 없다.** 1·2차 결과물도 아직 기기 미검증이다.
  PC에서 확인할 수 있는 것은 ZIP 구조·꼬리표·해시·보존 바이트까지다.
- `note.note` 의 `last edited page index` 가 새 쪽수를 넘을 때 클램프가 필요한지 **미확인**.
- 새 쪽으로 복제할 빈 `.page` 템플릿은 원본에 빈 쪽이 있어야 구할 수 있다. 원본이 전부 필기 쪽이면
  어디서 가져올지 **미정**.

## 다음 단계

1. `sdocx_transfer.py` 의 `_rewrite_archive` 를 **엔트리 추가·삭제까지 되게** 확장한다. 지금은
   기존 엔트리의 내용만 갈아 끼운다. 새 `.page` 를 넣으려면 기존 `.page` 엔트리의 로컬 헤더를
   본떠 이름만 바꿔 쓰는 경로가 필요하다(플래그 비트·날짜를 삼성 것과 같게 유지해야 한다).
2. `sdocx_rebuild.py` 를 새로 만든다. `MatchResult` 를 받아 출력 슬롯 목록을 만들고:
   매칭된 쪽은 옛 `.page` 를 `patch_page(pdf_page_index=...)` 로, 새 쪽은 빈 `.page` 를
   `patch_page(uuid=..., canvas=..., new_page_hash=...)` 로 복제, 옛 파일에만 있는 필기 쪽은
   옛 배경 페이지를 결과 PDF에 끼워 넣는다.
3. 결과 PDF는 `alignment.place_page` 로 슬롯마다 그린다.
4. `sdocx_note.PageOrder` 로 `pageIdInfo.dat` 을, `patch_note_height` 로 `note.note` 를 다시 쓴다.
5. `inspect_transfer` 가 쪽 구성이 같으면 기존 경로, 삽입·삭제가 있으면 재조립 경로를 고르게 한다.
6. UI: 매칭 표 렌더링 + 수동 수정(사용자가 요청한 형태).
