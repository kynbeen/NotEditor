공통 계층으로 편입**했고, 그 과정에서 발견한 기존 기능 회귀 2건을 고친 뒤 Notewise에도 본문 기준

- 새 테스트는 쪽 크기만이 아니라 **본문이 원래 자리로 돌아오는지**(원본 대비 4pt 이내)까지 본다.

### 버전을 깃 태그 하나에서만 — `41a4aaf`

- `noteditor/__init__.py` 의 `0.4.0` 과 릴리스 태그가 따로 놀아 어긋났다. 실제로 2026-08-28에
  배포 반영 여부를 버전으로 확인하지 못하고 쿠키 유무를 신호로 써야 했다.
- 출처를 순서대로 훑게 했다: `NOTEDITOR_VERSION` 환경변수 → `noteditor/_version.py`(배포 빌드 때
  태그에서 새기는 파일, 버전 관리 제외) → `git describe` → 배포 플랫폼 커밋 해시 → `0.0.0+unknown`.
- 태그를 붙였다 지우며 `0.5.0+dirty` / `0.0.0+<해시>.dirty` 로 바뀌는 것과, 새긴 뒤 `/api/health`
  가 `0.5.0` 을 보고하는 것을 실측했다.

### 접속자별 작업공간 격리와 정리 — `b536aab`, `11d57fc`

사용자가 "파일이 섞인다"고 보고했다. 세션 격리 구조 자체는 이미 있었고, **세 곳에서 샜다.**
전부 재현해 확인한 뒤 고쳤다.

1. **접속 한 번에 작업공간이 4개 생겼다.** 브라우저는 첫 화면과 정적 자산을 쿠키가 정해지기 전에
   병렬로 요청하는데, 미들웨어가 요청마다 작업공간을 만들었다. 주인 없는 임시 폴더가 만료(기본
   2시간)까지 남았다. 이제 첫 화면과 `/api/*` 만 만든다 → 접속 1회에 1개, 헬스 핑은 0개.
2. **사용자별 응답에 캐시 금지 헤더가 없었다.** `Cache-Control` 도 `Vary` 도 비어 있었다. 첫 화면
   응답에는 세션 쿠키가 실려 나가므로, 중간 프록시가 이를 저장하면 **다음 접속자에게 같은 세션
   쿠키가 배달된다.** 파일이 섞이는 가장 유력한 경로였다. `no-store, private` + `Vary: Cookie` 를
   붙였고, 서비스 워커도 그렇게 표시된 응답은 저장하지 않는다.
3. **지운 파일이 디스크에 남았다.** 문서를 목록에서 빼도 업로드 사본이 남았고, 읽을 수 없는 PDF라
   등록이 실패해도 받은 파일이 남았다.

그 위에 사용자 지적을 받아 한 번 더 고쳤다(`11d57fc`).

- **초기화를 도구별로 나눴다.** 처음 만든 `작업공간 비우기` 는 임시 폴더를 통째로 지워, 문서
  합치기를 정리하려 누르면 필기 옮기기에서 고르던 파일까지 사라졌다. 업로드 위치를
  `uploads/documents/` 와 `uploads/handwriting/` 로 나누고, 전역 버튼을 없앤 뒤 도구마다 자기
  버튼을 뒀다(`문서 비우기`, `선택 초기화`).
- **Notewise 저장 파일 이름이 `문서-필기.sdocx.notewise` 로 나가던 것을 고쳤다.** 내가 앞선
  커밋에서 넣은 회귀다. 화면이 확장자를 정할 때 쓰는 `source_format` 을
  `applyHandwritingResponse` 가 상태에 담지 않아 늘 `.sdocx` 로 굳었고, 서버가 그 뒤에
  `.notewise` 를 덧붙였다. 양쪽 다 고쳤다.
- 사용자가 물은 "같은 자리에 다시 올리면 앞 파일이 지워지는가"는 **이미 정상이었다.** 확인하고
  회귀 방지 테스트만 붙였다.

### 검증 방식

- 새 테스트가 정말 버그를 잡는지, **수정 전 커밋에 임시 작업 트리(worktree)를 만들어 돌려 확인**
  했다. 작업공간 격리 테스트 10개 중 7개가 실패했고(첫 로드에서 `5 != 1`), 파일명 테스트는
  `'target-필기.notewise' not found in "…target-필기.sdocx.notewise"` 로 실패했다.
- 실제 웹 서버를 띄워(TTL 3초·스윕 2초) 헤더·초기화·자동 정리가 도는 것까지 확인했다.

## 내린 결정과 근거

- **PR을 그대로 승인하지 않고 병합 커밋 위에 수정을 얹었다.** 기여자 크레딧을 이력에 남기면서도
  "내가 고친 부분"을 따로 볼 수 있다. PR #1은 병합으로 자동 종료됐다.
- **정렬 거부를 앞당기는 대신 실제 지원으로 갔다.** 배경만 다시 그리는 구조라 형식과 무관했고,
  이미 있는 `place_page` 를 그대로 쓸 수 있었다. 거절을 앞당기면 사용자는 여전히 못 하는 채로
  남는다.
- **버전을 태그 하나에서만 끌어온다.** 두 군데에 적으면 반드시 어긋난다. 이미 한 번 겪었다.
  빌드된 앱에는 깃이 없으므로 배포 빌드 때 파일로 새긴다.
- **초기화는 도구별로만 둔다.** 사용자가 "한쪽을 초기화하면 다른 쪽도 지워지면 안 된다"고 명시했다.
  전체를 한 번에 지우는 버튼은 두지 않는다 — 두 버튼을 누르면 같은 결과가 되고, 실수로 남의 작업을
  날리는 경로가 없어진다.
- **파일 삭제는 웹 쪽에서만 한다.** 데스크톱에서는 문서 목록의 경로가 **사용자의 원본 파일**이라
  지우면 안 된다. 그래서 `ComposerSession.clear_sources` 는 경로만 돌려주고, 실제 삭제는 임시
  폴더를 아는 `web.py` 가 한다. 이 경계를 지키는 테스트를 넣었다.
- **버전을 0.5.0으로 올리지 않았다.** 언제 어떤 번호로 릴리스할지는 사용자 판단이고, 올리려면
  `installer/NotEditor.iss` 폴백도 함께 손봐야 한다. 태그를 붙이는 순간 자동으로 맞춰진다.

## 미해결 질문 / 블로커

- **실제 `.notewise` 파일로 검증하지 못했다.** 합성 픽스처로만 확인했다. 특히 정렬을 켰을 때
  pymupdf로 다시 그린 배경 PDF를 Notewise 앱이 문제없이 여는지가 미확인이다. 정렬은 파일 구조가
  아니라 안에 들어가는 배경 PDF만 바꾸므로 위험이 크진 않지만, 확인이 필요하다.
- **배포 서버에 이미 저장된 캐시가 남아 있을 수 있다.** 캐시 금지 헤더가 없던 응답이 중간 캐시에
  들어갔다면, 배포 후에도 잠시 섞임이 보일 수 있다.
- Docker 이미지를 **실행**해 본 적이 여전히 없다(기존 열린 질문 그대로).
- 릴리스 태그를 붙인 적이 없어 설치 파일 산출과 새 버전 새김(`stamp_version`)의 실제 CI 동작은
  미검증이다. 로컬에서는 확인했다.
- 이 커밋의 CI 결과는 **미확인**이다. 푸시 직후 `queued` 상태만 봤다(run `33231497398`).
